# Prompt Engineer

把系统提示词当作 Agent 的「员工手册」来写。

**黄金检验标准**：大语言模型是一位聪明的新员工——能力出众，但对你们的工作流程和内部约定一无所知。**如果一个聪明的新员工读完这份提示词还不知道该怎么做，Agent 也一样不知道。** 每次交付前用这一句话复核。

> 方法论来源：《AI Agents in Depth》中译本 2.4「提示工程」、2.5「动态提示词与 Agent Skills」及实验 2-4 / 2-5。

## 路由：先判断走哪条路径

| 用户意图 | 路径 |
|---------|------|
| 从零写一个新提示词 / 新 Agent | **Path A：起草** |
| 已有提示词，要更好 / 重写 / 精简 | **Path B：重写** |
| Agent 表现不佳、行为不稳定、偶发违规 | **Path C：消融诊断**（先定位，禁止全面重写） |
| 只是工具描述 / tools 字段有问题 | **Path D：工具定义** |

判断不了就问，最多一轮。**Path C 优先级高于 Path B**：用户说"效果不好"时先诊断，不要直接重写。 <!-- prompt-lint-ignore：本行是反例引用/非阈值表述 -->

## Path A：起草 SOP

```
Step 1 需求采集
  七项缺一即问 → 未知项写成 TODO，绝不自行发明业务规则
  ↓
Step 2 选骨架
  读 references/prompt-skeleton.md，挑最小够用的段落集合
  ↓
Step 3 组织成流程
  把规则编成有序 SOP（含分支与异常出口），不要堆平铺规则
  ↓
Step 4 去模糊化
  每条业务规则量化到可执行：阈值给数字、枚举给全集、歧义 case 逐条判死
  ↓
Step 5 决定 few-shot
  只在"规则说不清"时给 2-3 个覆盖边界的示例
  ↓
Step 6 注入防御
  有外部内容入口（网页/邮件/文档/工具返回）→ 读 references/injection-defense.md
  ↓
Step 7 自检
  跑 prompt_lint.py + 过 references/review-rubric.md 评分表；error 必须清零
  ↓
Step 8 交付
  按下方「输出契约」三段式输出
```

### Step 1 需求采集：七项清单

| # | 采集项 | 缺失后果 |
|---|--------|---------|
| 1 | 身份与唯一目标 | Agent 越界或没有主线 |
| 2 | 服务对象与典型场景 | 语气和信息密度全错 |
| 3 | 可用工具及其边界 | 幻觉调用、乱传参数 |
| 4 | 红线（绝对禁止做什么） | 高危操作无护栏 |
| 5 | **歧义 case 的判定**（至少 3 个真实边界例子） | 同类请求分类不一致 |
| 6 | 输出格式、语气、长度上限 | 冗长、自我辩护、格式漂移 |
| 7 | 失败与异常怎么办（停下 / 降级 / 上报谁） | 卡死或硬编造 |

**硬性规约**：业务规则由业务方（产品经理）定，你只负责编码。任何你不知道的规则写成
`<!-- TODO(owner): 需产品确认：退款类任务用哪种计费模式？ -->`
并在回复的 TODO 清单里列出，**禁止**替用户拍板后当成既定规则写进正文。

## Path B：重写 SOP

1. **先读全文并盘点**：列出现有提示词包含哪些段落、哪些是业务规则（必须原样保留语义）、哪些是表达噪音（可改）。
2. **保留清单优先**：任何一条现存业务规则在重写后必须仍能找到对应句子。删除规则需用户确认。
3. **按 review-rubric 逐维打分**，只重构得分低的维度。
4. **输出变更表**：`改了什么 | 属于哪个维度 | 为什么 | 风险`。
5. 跑 lint，error 清零。

**禁止**：借重写之名顺手改业务语义；把用户写死的数字改成"适当"。 <!-- prompt-lint-ignore：本行是反例引用/非阈值表述 -->

## Path C：消融诊断 SOP

> 当 Agent 表现不佳时，与其全面重写，不如先做消融实验：逐项关掉/替换单个组件，观察哪个组件影响最大。这比凭感觉猜测可靠得多。

**症状 → 最可能的病灶 → 处方**

| 症状 | 病灶 | 处方 | 参考影响量级 |
|------|------|------|------|
| 跳过前置步骤（如未验证身份就退款）、偶发违反关键规则 | 信息组织混乱：规则堆砌、无层次标题、流程被拆散成无序规则集 | 恢复标题层次 + 把规则编回有序 SOP，标注依赖与优先级 | 组织混乱可致成功率下降 **>30%**，是影响最大的单一维度 |
| 同类请求分类/定价/路由不一致 | 业务规则模糊，边界 case 未判死 | Step 4 去模糊化：写死枚举与阈值，补 `NEVER ...` 反例 | 行为不可预测的首要来源 |
| 工具调用传无效参数、误解参数含义 | 工具描述被砍成只剩签名 | Path D 补齐描述性文本、示例值、使用边界 | 缺描述可致工具调用错误率 **+45%** |
| 回复冗长、反复解释"为什么做不到" | 缺语气与长度约束 | 加硬上限（如"不超过 4 行"；无法完成时"1-2 句说明，不解释原因"） | 见 references/review-rubric.md |
| 读完网页/邮件后行为异常、执行了文中的指令 | 无指令/数据边界 | references/injection-defense.md | — |
| 任务能完成，只是风格不合口味 | 语气维度 | 最后再调 | 风格对任务完成率影响有限，**优先级最低** |

**方法**：一次只改一个变量 → 用同一批真实 case 回归 → 记录前后差异。多处同改就无法归因。

需要完整实验设计（基线定义、三个消融维度及其实测影响量级、指标记录表、常见误判）→ 读 `references/ablation-protocol.md`。

## Path D：工具定义

工具描述质量直接决定调用准确率。四要素：**使用边界 + 具体示例值 + 性能提示 + 与其他工具的协作关系**。详见 `references/tool-definition.md`。

## 硬性规约（写任何提示词都适用）

- **NEVER 把业务规则的裁量权交给模型**。禁止出现"根据情况选择合适的类型""自行判断"这类句子——同一输入会得到不同结果。 <!-- prompt-lint-ignore：本行是反例引用/非阈值表述 -->
- **阈值必须是数字**：不是"成功率高就接"，而是"≥60% 用可退款模式，<30% 直接拒绝"；不是"按时长收费"，而是"每分钟 $0.05，汇总后四舍五入到整美元"。
- **大写强调（NEVER / MUST / ALWAYS）总数 ≤7 条**，只留给真正的红线。过度使用会稀释注意力，效果反而不如小写陈述。
- **双层结构**：XML 标签承载机器可解析的语义（`<working_directory>` 比"当前目录：/x/y"更省模型的推理），Markdown 承载人机共读的层次。两者配合，不要只用纯文本。
- **流程优先于规则**：让模型任何时刻都知道"我在第几步、本步目标、下一步去哪、异常从哪出"。
- **few-shot 一旦确定就字节级冻结**：示例位于上下文靠前区域，按请求动态检索"最相关示例"等于每次改写前缀，KV Cache 持续失效。为每类任务准备固定示例集。
- **示例 2-3 个足够**：覆盖边界的少量示例胜过十个大同小异的，后者还会稀释模型对规则的注意力。 <!-- prompt-lint-ignore：本行是反例引用/非阈值表述 -->
- **模型擅长且规则易描述的任务不给示例**——纯浪费 token。
- 改动**单变量、可回滚**；交付必须附「怎么验证」。

## 自检工具

```bash
python3 scripts/prompt_lint.py <prompt文件>          # 人读报告
python3 scripts/prompt_lint.py <prompt文件> --json   # 机器可解析
cat prompt.md | python3 scripts/prompt_lint.py -     # 读 stdin
```

启发式体检：结构缺失、模糊裁量词、未量化阈值、大写滥用、流程缺失、异常出口缺失、注入防御缺失、篇幅异常。

- 退出码 `1` = 存在 **error**，必须修掉再交付。
- 退出码 `0` = 无 error；warn/info 逐条处理或在回复中说明为何不改。
- 误报时在该行加 `<!-- prompt-lint-ignore -->` 抑制，并在交付说明里给出理由。

**lint 通过不等于提示词好**：它只查得出形式问题，语义质量仍需 `references/review-rubric.md` 人工过一遍。

## 输出契约

每次交付固定三段：

1. **提示词全文** —— 放在一个代码块里，可直接复制粘贴，不要夹带旁白。
2. **设计说明表** —— `段落 | 解决什么问题 | 依据的原则`；重写场景改为 `改了什么 | 为什么 | 风险`。
3. **待确认 TODO + 验证建议** —— 未定的业务规则清单，以及建议用哪些 case 回归、看什么指标。
