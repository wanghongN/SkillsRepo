# 提示词骨架与标签词汇表

## 双层结构原则

- **XML 标签**：机器可解析的精确语义。标签名本身携带信息——`<working_directory>/Users/project/src</working_directory>` 模型一眼就懂；纯文本"当前目录：/Users/project/src"还要先理解冒号前后的关系。
- **Markdown**：人机共读的组织逻辑，负责层次、清单、表格。
- 两者配合：XML 划分区块与来源，Markdown 组织区块内部。

## 最小骨架（按需增删，不要为凑齐而写空段）

```markdown
<identity>
你是 <名字>，<一句话职责>。服务对象是 <用户>，典型场景是 <场景>。
</identity>

<capabilities>
- 能做的事 1
- 能做的事 2
</capabilities>

<rules>
<!-- 红线在最前，大写强调总数 ≤7 -->
- NEVER <绝对禁止的高危行为>
- 默认行为：<最常见路径的默认动作>
- 冲突时的优先级：<A> > <B> > <C>
</rules>

<workflow>
## 标准操作流程
Step 1 <名称>：<目标>
  - 判据：<条件>
  - 异常 → <出口：停止 / 降级 / 询问用户>
  ↓
Step 2 <名称>：<目标>
  ↓
Step 3 验证：<怎么确认做对了>
</workflow>

<business_rules>
## <规则域名称>
| 输入情形 | 判定 | 数值/参数 |
|---------|------|----------|
| <边界 case 1> | <结论> | <写死的数字> |
| <边界 case 2> | <结论> | <写死的数字> |

- NEVER <把易混淆的两类情形明确分开的反例句>
</business_rules>

<output_format>
- 结构：<字段/章节>
- 长度：<硬上限，如不超过 4 行>
- 语气：<专业中立 / 轻松 / …>
- 无法完成时：<1-2 句说明，不解释原因，不自我辩护>
</output_format>

<examples>
<!-- 仅在"规则说不清"时保留；2-3 个覆盖边界；确定后字节级冻结 -->
<example>
<input>…</input>
<output>…</output>
</example>
</examples>

<external_content_policy>
<!-- 仅当会读取网页/邮件/文档/工具返回时保留，详见 injection-defense.md -->
</external_content_policy>
```

## 常用标签词汇表

| 标签 | 用途 |
|------|------|
| `<identity>` | 身份、职责、服务对象 |
| `<capabilities>` / `<tools>` | 能力清单、可用工具 |
| `<rules>` / `<constraints>` | 硬约束、红线、优先级 |
| `<workflow>` / `<sop>` | 有序流程与异常出口 |
| `<business_rules>` | 量化的业务判定 |
| `<output_format>` / `<response_style>` | 格式、长度、语气 |
| `<examples>` / `<example>` | few-shot |
| `<working_directory>` / `<environment>` | 运行时环境信息 |
| `<external_content source="...">` | 包裹不可信外部内容 |
| `<verification>` | 完成前的验证要求 |

## 段落顺序建议

身份 → 能力 → 红线 → 流程 → 业务规则 → 输出格式 → 示例 → 环境/外部内容策略。

理由：模型先建立"我是谁、不能做什么"，再进入"怎么做"。红线放在流程之后容易在长流程中被淹没。

## 流程写法：好 vs 坏

**坏（规则堆砌）**——同时适用多条时无从选择，未覆盖的情况无从推断：

```
- 文件不存在要报错
- 配置文件要备份
- 大文件要流式处理
- 处理完要校验完整性
- 要根据扩展名判断类型
```

**好（流程驱动）**：

```
File Processing SOP:
Step 1 Validation：检查文件是否存在且可读
  - 不存在 → 记录错误并停止
  ↓
Step 2 Classification：按扩展名 + 内容判定类型
  ↓
Step 3 Preprocessing：
  - 配置文件 → 先创建备份
  - >1MB → 流式处理
  ↓
Step 4 Execution：按类型执行核心逻辑
  ↓
Step 5 Verification：校验产出文件完整性
```

同样的信息量，后者让模型任何时刻都知道自己在第几步、当前目标、下一步去哪、异常从哪个出口走，而不必遍历规则表找匹配项。

## 业务规则去模糊化范例

**模糊**（同一任务不同时间会得到不同分类，业务逻辑不可预测）：

> 根据任务情况选择合适的计费类型。

**可执行**：

```markdown
计费模式判定（按顺序匹配，命中即停）：
1. 需要通过谈判降低现有账单 → percentage_based（抽取节省额的 20%）
2. 退款 / 取消订阅 / 其他服务性任务 → fixed_fee
   NEVER use percentage_based for refunds and service cancellations.
3. 预估成功率 <30% → 拒绝任务
   预估成功率 30%~60% → fixed_fee 且预收不可退
   预估成功率 ≥60% → 可退款模式

金额计算：
- 通话按 $0.05/分钟，汇总后四舍五入到最近整美元
- "节省"只基于当前账单金额计算，NEVER 把"避免未来涨价"计入节省
```

要点：顺序匹配消除重叠、阈值给数字、计费粒度写死、对最容易被模型自由联想的地方补一条 NEVER 反例。

## few-shot 决策

| 情形 | 给示例？ |
|------|---------|
| 期望输出难以用规则描述（文案风格、报告版式、客服语气分寸） | 给，2-3 个 |
| 存在少数高频边界 case，规则说清要一大段 | 给，专挑边界 |
| 模型本就擅长、规则三句话说清 | 不给，纯浪费 token |
| 需要按请求动态挑"最相关示例" | 不给——会破坏 KV Cache 前缀稳定性 |

放置位置：

- **系统提示词内**：成为静态前缀的一部分，对所有请求生效。默认选这个。
- **伪造首轮 user/assistant 消息**：适合按会话类型切换不同示例集。

两种位置都在上下文靠前区域，一旦确定就应保持字节级稳定。生产系统为每类任务准备**固定**示例集，不逐请求挑选。
