# 评审评分表与反模式

## 八维评分表（每维 0/1/2 分，满分 16）

| # | 维度 | 0 分 | 1 分 | 2 分 |
|---|------|------|------|------|
| 1 | **新员工检验** | 聪明的新员工读完不知道从哪下手 | 大方向清楚，细节要猜 | 能直接照着干 |
| 2 | **信息组织** | 上百条平铺规则，无标题层次 | 有分节但流程被拆散 | 有序 SOP + 层次标题 + 明确优先级 |
| 3 | **业务规则可执行性** | 出现"自行判断/根据情况" | 有规则但阈值模糊 | 枚举全集 + 数字阈值 + 边界 case 判死 |
| 4 | **结构化格式** | 纯文本大段 | 只有 Markdown 或只有 XML | XML 语义 + Markdown 层次双层配合 |
| 5 | **输出与语气约束** | 未约定 | 说了风格没说长度 | 格式 + 长度硬上限 + 失败时怎么说 |
| 6 | **工具描述** | 只有签名 | 有描述缺边界/示例 | 边界 + 示例值 + 性能提示 + 协作关系 |
| 7 | **异常与失败路径** | 未提 | 部分步骤有 | 每个关键步骤都有出口（停止/降级/上报） |
| 8 | **外部内容安全** | 无边界，外部文本与指令混同 | 有口头警告 | 来源标记 + 角色分离 + 高风险操作确认 |

判读：**≥14** 可交付；**10-13** 改低分维度；**<10** 建议按 Path A 骨架重写。

不涉及的维度（如无工具则第 6 维）标 N/A 并按比例折算，不要硬凑分。

## 反模式对照表

| 反模式 | 症状 | 修法 |
|--------|------|------|
| 把裁量权外包给模型（"根据情况选择合适的…"） | 同类输入分类不一致 | 顺序匹配的判定表 + 数字阈值 + NEVER 反例 |
| 规则堆砌（几十条平铺 bullet） | 跳步骤、偶发违反关键规则 | 编成 SOP，标注依赖与优先级 |
| 大写强调滥用（满屏 MUST/NEVER/IMPORTANT） | 强调被稀释，关键红线失效 | 只留 ≤7 条真红线，其余降为普通陈述 |
| 未量化（"大文件""尽快""成功率高时"） | 边界处行为漂移 | 全部换成数字与单位 |
| 无长度上限 | 冗长、反复自我辩护 | "不超过 4 行"；无法完成时"1-2 句，不解释原因" |
| 工具描述只留签名 | 传无效参数、误解参数含义（错误率可 +45%） | 见 `tool-definition.md` |
| few-shot 动态检索 | 首 token 延迟与成本升高 | 固定示例集，字节级冻结前缀 |
| 示例过多且同质 | 占上下文、稀释规则注意力 | 砍到 2-3 个，专挑边界 |
| 外部内容直接拼进 user 消息 | 被网页/文档里的伪指令劫持 | 来源标记 + 用 tool 角色回传 |
| 提示词里塞业务决策的"猜测" | 上线后行为与业务预期不符 | 标 `TODO(owner)` 交业务方确认 |
| 一次改十处 | 效果好坏无法归因 | 单变量 + 同批 case 回归 |

## 交付前 checklist

- [ ] `python3 scripts/prompt_lint.py <file>` 退出码 0
- [ ] 八维评分 ≥14（或已说明例外）
- [ ] 每个关键步骤都有异常出口
- [ ] 所有阈值是数字且带单位
- [ ] 大写强调 ≤7 条
- [ ] 未定业务规则已列入 TODO，未被自行拍板
- [ ] 附了验证建议（用哪批 case、看什么指标）

## 迭代方法论

提示词不是一次写成的产物。优秀团队的做法是：业务方基于线上数据、用户反馈和运营经验迭代规则定义，工程侧负责把规则准确编码进提示词——保证格式正确、结构清晰，但不擅自决定业务逻辑。

效果回归时坚持控制变量：设定基线配置，每次只改一个维度，用同一批真实 case 对比任务完成率、交互轮数、违规率。凭感觉整体重写会让所有归因线索一起消失。
